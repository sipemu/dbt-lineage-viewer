# Benchmarks

Two benchmarks: large projects built from real dbt SQL (below), and the
micro-benchmark of the graph builder on a synthetic 500-model project
(`cargo bench`, further down).

## Large projects from real SQL

`scripts/bench-scale/generate.py` builds dbt projects of 2k–20k models by
replicating five public projects (cal-itp data-infra, tuva, Fivetran
dbt_hubspot and dbt_jira, jaffle-shop) under renamed model, seed, snapshot and
source names, with refs, source() calls, macro arguments and YAML rewritten
to match. The SQL and Jinja are the projects' own, macros and installed
packages included. `scripts/bench-scale/run.py` times each operation and
reads peak RSS from the process's rusage:

```sh
python3 scripts/accuracy/run.py                     # check out the source projects
python3 scripts/bench-scale/run.py --sizes 2000,5000,10000,20000
```

Measured with dbt-lineage at commit `73fe08b` plus the column-lineage change
below, on an Intel Core i9-13900H (20 threads), 64 GB RAM, Linux 6.18, Rust
1.99. Each cell is wall time and peak memory of one run.

| Operation | 2,205 models | 5,594 models | 10,562 models | 20,498 models |
| --- | ---: | ---: | ---: | ---: |
| graph build, cold | 0.23 s · 25 MiB | 0.44 s · 44 MiB | 0.90 s · 93 MiB | 1.75 s · 159 MiB |
| graph build, cached | 0.21 s · 25 MiB | 0.45 s · 44 MiB | 0.79 s · 75 MiB | 1.53 s · 136 MiB |
| lint | 0.34 s · 25 MiB | 0.75 s · 44 MiB | 1.40 s · 75 MiB | 2.71 s · 136 MiB |
| column lineage | 1.90 s · 2,318 MiB | 3.75 s · 4,524 MiB | 6.32 s · 7,166 MiB | 11.30 s · 11,421 MiB |
| ci report (1 file changed) | 2.45 s · 48 MiB | 6.48 s · 75 MiB | 10.58 s · 132 MiB | 21.14 s · 243 MiB |
| static site | 1.83 s · 2,446 MiB | 4.45 s · 4,296 MiB | 7.64 s · 6,690 MiB | 16.92 s · 10,417 MiB |
| LSP: open file → diagnostics | 0.24 s · 27 MiB | 0.46 s · 45 MiB | 0.84 s · 76 MiB | 2.02 s · 137 MiB |

Everything grows linearly: from 2.2k to 20.5k models (9.3×), time grows
6–9×. The warm cache barely helps at this size: loading it costs about as
much as parsing.

**Column-lineage memory is the outlier.** It comes from the regex fallback
analyzer (`src/parser/column_lineage.rs`), whose per-thread regex cache keeps
three compiled case-insensitive Unicode regexes per distinct column name,
unbounded: 1.4 GB on one thread at 2.2k models, 4.1 GB on twenty. The CLI now
runs that analyzer only on models the AST analyzer produced nothing for (its
other output was dropped anyway), which cut 2.2k-model column lineage from
3.9 GB to 2.3 GB with identical output; the cache itself still needs a bound.
`site` computes the same lineage and has the same profile. `ci report`
analyzes only the changed part of the graph and stays small.

CI runs the 2k and 10k sizes weekly (`.github/workflows/accuracy.yml`).
Runner hardware varies, so it gates on scaling rather than absolute time: the
job fails when an operation's time grows more than twice as fast as the
project (`--max-scaling 2`). `--baseline` / `--write-baseline` compare
absolute times against an earlier run on the same machine.

## Graph builder micro-benchmark

Baseline numbers for the SQL-parse-mode graph builder. Generated by
`cargo bench --bench builder_bench`. Numbers below are from a single
machine (Linux, AMD64, Rust stable). Use them as relative references,
not absolute targets.

### Fixture

`benches/builder_bench.rs` generates a synthetic 500-model dbt project
into a temp directory on first invocation:

- 200 staging models, each ~6 lines of SQL with one source reference.
- 300 mart models, each ~8 lines of SQL with two ref calls (one via a
  detected wrapper macro to exercise #13).
- One `schema.yml` per layer with model descriptions.
- One macro file defining a simple `ref()` wrapper.

Total: 500 nodes, 500 `ref()` calls, 200 `source()` calls.

### Baseline (0.5.1)

| Target | Time | Notes |
|---|---|---|
| `build_graph_cold` (no cache) | **~17 ms** | Parses every file from scratch. Rayon parallelization across cores. |
| `build_graph_warm` (cache hit) | **~4.3 ms** | Cache populated by a prior cold run. Walks dirs + hashes files + serves cached parse. |
| `compute_summary` | **~114 µs** | Aggregation only — no I/O. |
| `compute_impact` | **~1.3 µs** | BFS from a deep-fan-in staging model. |

**Warm vs cold ratio: ~4×.** The warm path skips the lexer + regex
parsing entirely, just walks dirs and hashes file contents. The ratio
grows on real projects where model files are larger and parsing is
proportionally heavier.

### Lexer overhead (#25)

Cold parse went from ~14.4ms (0.5.0, regex-only) to ~17ms (0.5.1, with
Jinja+SQL lexer in the path). The ~15% extra buys correctness — false
positives from `ref(` inside string literals and comments are now
eliminated. Worth it.

### Reading the numbers

For context: 14.4 ms cold means a 500-model project rebuilds the full
graph in well under a frame on a developer laptop. 5.2 ms warm is
sub-frame, effectively instant. The cache earns its keep most on
projects where:

- Models are large (heavy Jinja, many lines of SQL).
- The user runs `dbt-lineage` repeatedly (TUI dev loop, CI watch).

### Regression policy

When changes to the parser, builder, or cache affect these numbers,
update this file in the same commit. CI doesn't gate on bench
performance yet — these are reference numbers for humans.
